# 性能与容量基线

本文记录 1.0.0 在发行规格下（`us-west-2`）的性能、容量、新鲜度与成本基线，以及端到端分段计时的结果。所有数值都来自实际 AWS 测量，执行依据是测量前固定的执行清单（矩阵、请求数、预热、采样窗口、每项 3 轮与停止条件）。

项目没有约定的 SLA 目标，因此不按目标判定 PASS：目标状态记为 `NO_CONFIRMED_TARGET`。1.1.0 的规格相同，未重测。下面的数值只是[发行规格](release-notes.md#规格)下测得的基线，不应外推为其他规格或负载下的容量。

## 方法

- 每个单元格跑 3 轮。预热请求（同步写 8 个、接入 4 批、查询 2 条）不计入统计，并使用独立的 Idempotency-Key。
- 每个请求都是一个样本：拒绝（422 / 429）、超时和 UNKNOWN 都计入分母。UNKNOWN 只按原 `write_id` 读取原回执来核对，从不重放。
- 延迟取 nearest-rank 百分位，按“单元格 × 轮”计算；样本少于 100 个时不报告 p99（表中标为“样本不足”）。同步写另给出三轮合并的 p99，并明确标注。
- 正确性：
  - 同步写：每个单元格按实际提交序号回放出独立的预期状态，与实际行（有序摘要）比对。
  - 接入：每个已受理批次都必须以原生账本中的 `COMMITTED` 结束，全部事件的数量与金额之和精确一致。
  - 查询：读取固定的数据版本，与独立预期比对。
- 分段计时：启用 `Timing=on` 时，同步代理、接入、写者和查询进程各输出一行 `COLVENNA_TIMING` JSON。这些行通过 `write_id`、`ingestion_id`、`query_id` 与客户端样本关联。所有区间以毫秒为单位，按进程单调时钟计量；嵌套区间（如 `writer.*` 落在 `writer_rpc` 之内）保持各自的进程归属，父区间中无法归因的部分记为 `unattributed`。计时行不含凭证、SQL 文本或记录内容，报告中有自动检查。

## 测量内的失败与补充核对

测量中有 3 项核对在运行时记为 FAIL，原因都在核对方式，不在数据。它们由下表的补充核对替代，原始结果保留不改。

| 原核对 | 原因 | 补充核对 | 结果 |
| --- | --- | --- | --- |
| `ingestion-all-cells-exact-events` | 接入矩阵刚结束时，核对查询超过 30 秒默认时限（`QUERY_TIMEOUT`）；另外，预期值漏算了它读取到的预热批次 | 以 `timeout_ms=300000` 只读测量批次（批次序号 < 900） | PASS：1,015,632 条事件、金额合计 506,885,177.52 与独立预期一致，查询 5.8 秒 |
| `overload-no-lost-duplicated-or-half-commit` | 过载结束后的回放核对查询超过 30 秒默认时限 | 一次分组读取全部 932 个 key 块，逐块对照按提交序号回放的预期 | PASS：0 个不一致块；读取版本 6975 ≥ 最高已提交序号 6378 |
| `timing-overhead-measured-on-and-off` | 测量工具只统计 200 应答；同一单元格中执行前被拒的 429 和随后核对到终态的 504 都是确定结果 | 两种模式都要求 96 个请求全部得到确定结果 | PASS：两种模式各 96/96 |

执行清单随后加入了这一调整：事后核对使用 `timeout_ms=300000`，只计测量批次。第一项失败同时揭示一个需要公布的容量特征：大量写入刚结束时，读取同一张表的查询会明显变慢，见下文“写入高峰期间及之后的查询”。

## 结论与主要瓶颈

**同步写**

- 写者串行执行原生提交。单行请求在并发 1 时约 1.0 秒：同步代理约 0.8 秒，其中写者事务单元约 0.4 秒；其余是 API Gateway 与 Lambda 的开销。
- 并发达到 4 以上时，吞吐饱和在约 2.0–2.4 次提交/秒。继续增加的并发只体现为写者调度等待：并发 16 时约 5.5 秒。
- 行吞吐取决于批大小：
  - 1 行一批约 2 行/秒；
  - 10 行约 20 行/秒；
  - 100 行约 120 行/秒；
  - 1000 行约 240–280 行/秒，此时一次业务 SQL 约 3.6 秒，因为同步写仍然逐行执行语句。
- 1000 行、并发 8 和 16 时，写者等待预算耗尽：
  - 一部分请求在执行前被拒，返回 `429 WAIT_BUDGET_BEFORE_EXECUTION`，不产生效果；
  - 一部分返回 `504 WRITE_WAIT_TIMEOUT`，之后按 write_id 核对到终态。
- 全部 60 个单元格的实际行都与独立回放一致。

**异步接入**

- 本轮使用 `b2cb808` 的批量写入。写者事务单元的耗时：1 条记录约 0.25 秒，1,000 条约 0.6 秒，5,000 条约 1.9 秒（其中原生 SQL 约 1.36 秒）。
- 每个 FIFO 组按顺序处理：1 条一批的批次每秒只能提交 1–2 个。大批次时提交速率在 570–1,970 条/秒之间。
- 同一单元格的速率从第 1 轮到第 3 轮持续下降（例如 1000×16：1,233 → 954 → 569 条/秒）。同期 `ods.perf_events` 增长到约 120 万条事件，每批的读取与写入成本随表增大而增加。超过这个规模的容量没有测量。
- 受理接口 p50 约 0.9–3.8 秒，包括 schema 校验（5,000 条约 0.9 秒）、S3 归档和 SQS 发送。表中的“受理→提交可见”由测量工具逐个轮询全部待定原件得到，是上界。服务端的排队等待和事务单元见下表。

**长任务导入**

- 发布导入仍是逐行语句、每块 512 行：
  - 20 万行（391 块）从运行开始到发布用了 22.2 分钟，约 150 行/秒；
  - 混合与过载期间的 10 万行（196 块）分别用了 14.7 和 24.6 分钟。
- 导入与接入、同步写由公平调度交替执行，任何一类都没有被饿死。

**查询**

- 每条查询都在新进程中执行：原生打开约 3 秒，是延迟的下限。冷进程的服务端耗时 p50 约 4.2–5.7 秒，与查询形状关系不大；读取 101 万条事件时暂存约 1.8 秒。任务启动后的首条查询约 7.8 秒。
- 本轮没有热缓存：查询进程之间不保留原生缓存，因此记为 `NOT_APPLICABLE`。
- 结果保留配额实测：连续提交时，第 65 条查询以 `QUERY_RESULT_RETENTION_QUOTA` 被拒（前 64 条成功，398.7 秒）。

**写入高峰期间及之后的查询**

- 混合负载期间，6 条聚合查询中只有 2 条成功（13.8 秒、26.9 秒），另外 4 条超过 30 秒默认时限。
- 接入矩阵和过载阶段刚结束时，各有一条核对查询超时。同样的读取在数十分钟后只需 6–36 秒。
- 因此，写入高峰期间或刚结束时的分析查询应设置更长的 `timeout_ms`（最大 300,000），或者错开写入高峰。

**并行与过载**

- 混合负载下：同步写 140/144 提交（2 个 429、2 个 504 均已核对）；539 个接入批次全部提交；10 万行导入照常发布；提交序号唯一；停止负载后用 744 秒排空。
- 过载下：API Gateway 限流与写者背压在执行前拒绝了 3,675 个同步写和 1,265 个接入批次。
  - 7 个同步写原件以 `503 WRITE_RESULT_UNKNOWN` 结束，落定窗口后仍没有原生提交，可以用原 Idempotency-Key 恢复一次；
  - 没有丢失、重复或半提交的效果（见上文的过载核对）；
  - 停止负载后用 1,377 秒排空。

**计时开销与资源**

- 开启计时与关闭计时相比，同一单元格的 p50 为 1,832 ms 对 1,838 ms，差异在测量噪声之内。
- 本轮写者进程的 RSS 峰值为 2,303 MiB（任务内存 4 GiB）。

## 新鲜度

- 接入：受理后进入原生账本，在没有积压时约需写者事务单元的时间（0.25–1.9 秒），加上 consumer 的轮询间隔。积压时再加上排队等待：16 个生产者时，1000 条和 5000 条一批的 p50 分别为 16.6 秒和 23.7 秒。
- 分析发布：一次 orders 流水线（writer SQL → Lambda pandas → ECS SQL → writer SQL）从提交运行到 `PUBLISHED` 约 3 分钟（隔离还原后的一次运行）。

## 成本范围

均为 us-west-2 的公开单价（2026-10-18 经 AWS Price List API 读取，见 [prices.py](../src/colvenna_isle/control/prices.py)），不含免费额度、Savings Plans 与税费，不是账单。

- **常驻部分**：写者与查询两个 ARM Fargate Task（各 2 vCPU / 4 GiB），合计约 0.158 USD/小时，30 天约 114 USD。
- **计量部分**：产品自身的成本报告（测量窗口 4.9 小时）中，已计量工作负载共 0.0956 USD：写者计算 0.0793、查询计算 0.0157、Lambda 0.0005；S3 请求和存储在报告精度下为 0。
- **不计价**：NAT、ALB、VPC 端点、API Gateway、CloudFront、DynamoDB、SQS、CloudWatch、数据传输、SlateDB 原生存储、接入归档与暂存对象。这些费用取决于账号已有的设施和流量。
- 包含上述各项的每月粗估（按数据档位）见[成本估算](cost-estimate.md)。

## 未运行或未验证

- 其他规格、多个写者、拆库、其他区域：未运行。
- 按轮计算的 p99：每个单元格每轮 48 个样本，少于 100，因此只报告三轮合并的 p99，并在表中注明。
- Query Editor 与 Admin Console 的页面延迟：没有测量。
- `ods.perf_events` 超过约 120 万条事件之后的接入与查询容量：没有测量。
- `after_write` / `after_ingestion` 大快照：已知限制，见[发行说明](release-notes.md#限制)。
