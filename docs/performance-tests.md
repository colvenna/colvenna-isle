# Colvenna Isle 性能测试说明

本文定义性能与容量测试：测什么、在什么环境下测、怎样执行、怎样判定。1.0.0 在发行规格下的实测结果见[性能与容量基线](performance.md)。

## 1. 与 UAT 的关系

- [UAT](uat/test-cases.md) 只包含功能用例，**默认不执行性能测试**，性能结果也不是发行门槛。
- 性能测试按需单独执行，适用于以下情况：
  - 规格、存储引擎或写入路径改变之后；
  - 需要评估某个负载能否承载时。
- 性能测试会产生持续负载与大量数据，必须在独立环境中执行，不与 UAT 或业务环境共用。

## 2. 目标与判定

- 目标是测得给定规格下的基线：吞吐、延迟分布、积压与排空、新鲜度、资源与成本，并找出主要瓶颈。
- 项目没有约定 SLA。吞吐和延迟不按目标判定 PASS / FAIL，只报告实测值，并注明规格与负载。
- 正确性必须在整个测量过程中保持。任何一项正确性核对不一致，该次测量即无效，需要先找到原因：
  - 不丢失、不重复、没有半提交；
  - 提交序号唯一；
  - 查询结果与独立预期一致。
- 有约定目标时，按完整的约定负载判定，不删除慢请求，也不缩短测量窗口。

## 3. 环境

| 项目 | 要求 |
| --- | --- |
| 环境 | 用 [`install.sh`](installation.md#快速安装installsh) 安装的独立环境，安装后不做调优 |
| 空间 | 专用测量空间，测量前为空 |
| 规格 | 与[发行规格](release-notes.md#规格)一致：写者与查询各 1 个 2 vCPU / 4 GiB Task，DuckDB `memory_limit` 512 MB、2 线程 |
| 分段计时 | 需要分段数据时，在关闭状态下执行 `admission.py timing --timing on`（见[安装部署手册](installation.md#9-开放关闭与计时)） |
| 记录 | 源码 commit、release manifest digest、环境名、测量窗口 |

## 4. 测试矩阵

每个单元格跑 3 轮。预热请求不计入统计，并使用独立的 Idempotency-Key：同步写 8 个、接入 4 批、查询 2 条。

| 类别 | 负载 | 每个单元格 |
| --- | --- | --- |
| 同步写 | 直接表上 insert / upsert / update / delete 交替；每批 1 / 10 / 100 / 1,000 行 × 并发 1 / 2 / 4 / 8 / 16；`timeout_ms` 20,000 | 每轮 48 个请求 |
| 异步接入 | 每批 1 / 100 / 1,000 / 5,000 条 × 生产者 1 / 4 / 16 | 每轮 48 批（5,000 条一批时 12 批） |
| 查询 | 点查、范围、聚合、排序、发布版本全表扫描、百万级事件聚合；current 与 published 一致性；冷进程与新任务首查询 | 每种形状每轮 6 条，并遵守结果保留配额（见第 6 节） |
| 混合负载 | 同时运行 300 秒：同步写（10 行、并发 4）、接入（100 条、4 个生产者）、10 万行分块导入、每 20 秒一条聚合查询 | 1 次 |
| 过载 | 同时运行 120 秒：同步写（100 行、并发 32）、接入（1,000 条、16 个生产者）、10 万行分块导入 | 1 次 |
| 计时开销 | 同一单元格（10 行、并发 4，96 个请求）分别在 `Timing=on` 与 `off` 下执行 | 各 1 次 |

## 5. 指标与统计

- 每个请求都是一个样本，拒绝（422 / 429）、超时和 UNKNOWN 都计入分母。
- UNKNOWN 只按原 `write_id` 或 `ingestion_id` 读取原回执来核对，从不重放。
- 延迟取 nearest-rank 百分位（p50 / p95 / p99），按“单元格 × 轮”计算。样本少于 100 个时不报告 p99；需要时给出合并多轮的 p99，并注明合并。
- 指标：
  - 请求 / 秒与已提交行（条）/ 秒；
  - HTTP 结果分布；
  - 受理到提交可见的时间；
  - 积压与停止负载后的排空时间；
  - 写者进程 RSS；
  - 产品成本报告。
- 分段：用 `COLVENNA_TIMING` 行按 `write_id`、`ingestion_id`、`query_id` 关联到客户端样本。
  - 写者调度等待、事务单元、业务 SQL、原生 COMMIT 等分段各自报告；
  - 父区间中无法归因的部分记为 `unattributed`。

## 6. 正确性核对与执行注意事项

| 核对或注意事项 | 做法 |
| --- | --- |
| 同步写 | 每个单元格按实际提交序号回放出独立的预期状态，与实际行（有序摘要）比对 |
| 异步接入 | 每个已受理批次都以原生账本中的 `COMMITTED` 结束；全部事件的数量与金额之和精确一致 |
| 查询 | 读取固定的数据版本，与独立预期比对 |
| 过载 | 按 key 分块对照回放结果，确认没有丢失、重复或半提交；读取版本不低于最高已提交序号 |
| 写入高峰之后的核对查询 | 设置 `timeout_ms=300000`：大量写入刚结束时，读取同一张表的查询会明显变慢 |
| 查询轮次 | 整个环境最多保留 64 个结果、每个保留 10 分钟。查询轮次之间需要留出间隔，否则以 `429 QUERY_RESULT_RETENTION_QUOTA` 失败 |
| 限流 | API Gateway 默认 10 rps、突发 20，过载场景中的 429 属于预期结果，计入分母 |
| 活动空间 | 写者进程最多打开 2 个空间的数据库；测量只使用一个空间 |

## 7. 结束与清理

- 停止负载后，核对全部原件到终态，确认调度已排空、接入队列与 DLQ 为空。
- 保留原始样本、计时行与成本报告。
- 不再需要测量环境时，用 [`uninstall.py`](installation.md#12-卸载) 删除。

## 8. 报告

报告至少包括：

- 第 3 节的环境记录；
- 每个单元格的吞吐、延迟分布、HTTP 分布与正确性结果；
- 混合与过载的进展、积压和排空；
- 分段计时与计时开销；
- 资源与成本范围；
- 主要瓶颈；
- 未运行或未验证的项目。

格式可参考[性能与容量基线](performance.md)。

测量用的负载驱动程序不随仓库发布。产品自带的分段计时（`COLVENNA_TIMING`）和成本报告提供服务端数据，客户端按本说明的矩阵与统计方法记录样本。
